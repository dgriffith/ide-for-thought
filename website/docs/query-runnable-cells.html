Runnable cells

A fenced ```sparql or ```sql code block in a note isn't just a syntax-highlighted example — it's a query you can actually run, with the result landing right below it. Same run mechanism as ```python cells, covered in Editor.

Running a query cell

Click the ▶ icon in the gutter next to a ```sparql or ```sql fence, or place your cursor in it and press Cmd/Ctrl+Shift+Enter. The result lands in a sibling ```output block immediately after — the editor manages that block for you; don't hand-write one, since it gets overwritten on the next run.

Auto-injected prefixes

You only need to write the SELECT/ASK/CONSTRUCT body — these are already in scope for every SPARQL cell (and every query run from the Query panel):

minerva:
Minerva's own ontology — notes, tags, links.
thought:
The Thought ontology — claims, grounds, warrants, and the rest of the epistemic vocabulary.
dc:
Dublin Core — titles, creators, dates.
rdf: / rdfs:
The RDF and RDF Schema basics — rdf:type, rdfs:label, and so on.
xsd: / csvw: / prov:
Typed literals, CSV-table metadata, and provenance.

Tables from markdown

A markdown table in your notes is queryable as SQL the moment it's saved — column headers become the schema, via CSVW. The table's name is auto-derived from the CSV's relative path (e.g. notes/data/2024-experiment.csv becomes notes_data_2024_experiment), or you can set one explicitly with table_name in that file's frontmatter. See Tables & CSV for how a table gets registered in the first place, and Query menu & panel's Stock SQL queries for how to check a table's schema before you write against it.

SQL executor details

SQL cells run through DuckDB. Values that don't map cleanly to JSON — BigInt, dates, nested types — are normalized on the way out (BigInt to a plain number when it fits safely, otherwise a string; dates to ISO strings) so the output block is always valid JSON.
