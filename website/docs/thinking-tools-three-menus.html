Docs/Thinking tools/The three menus

The three menus

Every skill declares exactly one menu — Learning, Research, or Analysis — in its frontmatter, and that's the only thing that decides where it shows up in the menu bar (and in the command palette's grouping). The three aren't enforced categories with different capabilities; they're a rough division of labor: Learning helps you understand something already in front of you, Research goes out and gathers or files new material, Analysis operates on a claim or argument you already have. A skill's menu: field is just a label — nothing about outputMode, tool access, or approval tier changes based on which one it picks.

What belongs where

The order in the menu bar itself — Learning, then Research, then Analysis — is deliberate: it reads top-down as a workflow, read-and-understand first, then go gather or file material, then operate across what you've collected (src/main/menu.ts, the comment above buildToolMenus()). A couple of real stock skills per menu, with the actual frontmatter fields that place them:

Learning
Skills that work on something you already have open — explain it, expand it, quiz you on it. Deep Dive on Term (src/main/skills/stock/deep-dive.md) expands a selected word or phrase into a fuller explanation at a chosen depth, using the surrounding note as context. Explain Like I'm… (src/main/skills/stock/explain-like-im.md) and Quiz Me (src/main/skills/stock/quiz-me.md) are the same shape: no new material comes in from outside, the skill just changes how you're engaging with what's already there.
Research
Skills that go get something — from the web, from your existing notes, or from a source you're reading — and hand it back as a draft to file. Find Sources (src/main/skills/stock/find-sources.md) assembles a candidate reading list from web search and your existing notes; it explicitly doesn't ingest anything itself — "You pick which to actually read; ingest the keepers through Ingest URL / Identifier." Extract Key Claims (src/main/skills/stock/extract-key-claims.md) mines a source for thought:Claim notes anchored back to the passage they came from. Check Facts (src/main/skills/stock/check-facts.md) verifies a specific claim against outside evidence.
Analysis
Skills that operate on a claim, argument, or note you already have, teasing out structure, tension, or a stronger version of it. Steelman (src/main/skills/stock/steelman.md) constructs the strongest possible version of an opposing argument. Find Tensions (src/main/skills/stock/find-tensions.md) compares two notes for where they disagree. Doublecrux and Murphyjitsu are the same family — this is Minerva's largest menu by a wide margin, roughly 30 of the ~50 stock skills, which is exactly why it's the one that needed grouping.

Thematic grouping within a menu

A skill's frontmatter can carry an optional group: field — a short thematic label like Disagreement, Verification, or Data. When at least one skill in a menu sets a group, that menu stops rendering as a flat list and becomes a set of nested submenus instead, one per group name, in first-appearance order (which follows the menu config's ordering). Skills that don't set a group collect into a trailing General bucket rather than disappearing. Steelman and Doublecrux both set group: Disagreement; Find Sources sets group: Discovery; Check Facts, Date / Scope Check, and Find Primary Sources all set group: Verification.

Flat until someone sets a group — where this is enforced

The partitioning is pure logic in groupToolsByGroup() (src/shared/tools/grouping.ts): it buckets tools by their group field in a Map keyed by first appearance, collects ungrouped tools separately, and — critically — "if no tool in the list declares a group, the result is a single null-labelled bucket." hasNamedGroups() checks whether any bucket has a non-null label. buildToolMenus() in src/main/menu.ts (lines 593–608) calls both: when hasNamedGroups() is false it renders tools.map(mkItem) directly as a flat list; only when it's true does it wrap each bucket in a submenu entry, labelled from g.label or falling back to 'General' for the trailing bucket. No stock skill in Learning or Research sets a group today, so both stay flat — Analysis is the only menu with named groups (Disagreement, Verification, Discovery, Data, Semantic, Pattern, Motivation, Planning, Diagnostic, Generation, Organization, Mining, Decomposition, Summarize, Argumentation), which is also why it's the menu large enough to need the split. The same groupToolsByGroup() call is the one place this logic lives — the renderer's own copy of the registry and the Settings → Skills UI both read the same group field, so a skill you group yourself behaves identically everywhere it appears.

Gotchas

  • The menu is just a label, not a capability tier. Nothing about a skill's outputMode, tool access, or approval tier is derived from which of the three menus it's in — menu: only controls where it's discoverable. A Research skill and a Learning skill can both open a conversation, write a note, or call the same tools; there's no sandboxing by category.
  • A skill can't belong to more than one menu. menu: takes a single value. If a skill feels like it straddles two categories, pick the one that describes what triggers you to reach for it, not what it technically does under the hood.
  • Adding a group to one skill doesn't just nest that skill. Because grouping is a menu-wide decision (hasNamedGroups() flips for the whole category), setting group: on a single skill in an otherwise-flat menu immediately restructures every other skill in that menu into the trailing General bucket. If you're authoring a skill for Learning or Research today, adding a group is a visible change to the whole menu, not a local one.
  • Source-scoped skills never appear in these menus at all. A skill with scope: source is excluded from Learning/Research/Analysis and the editor's right-click menu regardless of what menu: it declares — it only shows up in the Source viewer's Tools menu. See What thinking tools are for that split.
