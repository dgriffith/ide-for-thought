Highlights

Wrap text in double equals signs and Minerva marks it as highlighted — a tinted inline span, the same idea as a highlighter pen on paper. It's a lightweight way to flag a passage as important while you're reading or drafting, without committing to a claim, a link, or any other structured markup.

Syntax

The marker is == on both sides of the text. An optional color name before the text picks from a small built-in palette; leave it off for the default tint.

==text==
Highlight. Marks the enclosed text with the default tint.
==color:text==
Colored highlight. color must be one of yellow, green, blue, pink, or orange. Anything else isn't recognized as a color prefix and is treated as part of the highlighted text instead — so ==Pythagorean: a²+b²== highlights the whole string rather than guessing at a color.
no space inside
Whitespace guard. A space or tab right after the opening == or right before the closing == stops the match — same rule as **bold** and ~~strikethrough~~. This keeps a run of prose like x == y == z from accidentally turning into a highlight.
===
Not a delimiter. Three or more consecutive equals signs — in either direction — are never read as a highlight marker, so ASCII rules and similar runs of = are left alone.

The migration is safe as long as ==the backfill runs before the

How highlights render

A highlight becomes a <mark> element wherever it appears — an inline tinted span, not a block. In the rendered preview this shows as a soft color wash behind the text, sized to the palette color you chose (or the default accent tint if you didn't choose one).

Screenshot — Highlighted text in preview
A rendered paragraph mid-sentence with two inline highlighted spans: one with the default tint around a short phrase, and one with the yellow palette color around a different phrase later in the same paragraph — both shown as a soft color wash behind the text, inline with the surrounding prose.

In the source editor, the same span is painted with a matching tint while you type — the == delimiters stay visible rather than being hidden, which is the convention Minerva uses for inline markup generally (it matches how *emphasis* and ~~strikethrough~~ are shown). You can see exactly what you wrote, decorated in place.

The color is themeable

Highlight tints are defined as CSS custom properties per theme, not fixed colors — the same five palette names (yellow, green, blue, pink, orange) resolve to different underlying values in Honey, Light, and Contrast, so a highlight stays legible and on-palette no matter which theme you're using. The editor and preview both derive their tint from the same source, so a highlight looks the same intensity in both places.

Gotchas

  • Other inline formatting nests fine. The text inside ==…== is re-parsed as regular inline markdown, so ==**bold**==, ==[[wiki-link]]==, and similar combinations work as you'd expect — the highlight wraps around the other formatting rather than blocking it.
  • Bold can wrap a highlight too. **==highlighted==** resolves outermost-in — the bold applies around the highlighted span — so both directions of nesting are supported.
  • Unrecognized color prefixes aren't stripped. Only the five palette names count as a color. ==note:remember this== isn't read as a note-colored highlight — the whole thing, prefix included, is just the highlighted text.
  • An empty color prefix falls back to plain. ==yellow:== has no body left after the color name, so it isn't treated as a valid highlight with an empty label — it's left uncolored so you can still see what you wrote.
  • Highlights are inline-only. A newline inside the marker ends the match before it closes — a highlight can't span multiple lines or wrap a whole paragraph.
