Docs/Notes/Links

Links

Wiki-links are how notes connect to each other. Wrap a note title in double brackets and Minerva turns it into a live link — resolved, rendered, and indexed into the knowledge graph. Beyond a plain reference, a link can carry a type: supports, rebuts, depends on, and nine others that describe the shape of the relationship, not just its existence.

Syntax

The full form is [[type::target#anchor|display]] — every part after the target is optional.

[[target]]
Basic link. target is a note title or filename. An untyped link is a References link — the default, catch-all type.
[[target|display]]
Display text. Everything after | is shown in place of the raw target — useful when the note title is long or reads awkwardly inline.
[[target#Heading]]
Heading anchor. Points at a specific heading in the target note rather than the top of the file.
[[target^blockid]]
Block anchor. Points at a specific block. The ^ is part of the syntax and isn't stripped when Minerva writes the anchor into the graph.
[[type::target]]
Typed link. type must start with a lowercase letter (e.g. supports, depends-on) — see the full list below. It goes before the target, separated by ::.

Anchors and display text combine with a type prefix in any order you'd expect:

This claim is well established.[[supports::experiment-log#Trial 4]]

See [[depends-on::auth-redesign|the redesign proposal]] before touching this.

Typed links

A typed link renders in its type's color in preview, so the shape of a note's connections is visible at a glance without opening the backlinks panel. Twelve types are built in:

references
References. General-purpose "points at" link. The default when no type is given.
supports
Supports. This note backs up the claim in the target.
rebuts
Rebuts. This note argues against the target.
load-bearing-for
Load-bearing for. Flags the target as critically dependent on the analysis in this note — a high-leverage link worth double-checking if this note turns out to be wrong.
expands
Expands. This note elaborates on or goes deeper into the target.
depends-on
Depends On. This note requires the target to hold.
implements
Implements. This note is a concrete realization of an idea or spec described in the target.
alternative-to
Alternative To. This note proposes a different approach to the same problem as the target.
supersedes
Supersedes. This note replaces the target — a signal the target may be stale.
related-to
Related To. A loose, non-directional relation — useful when a link matters but none of the sharper types fit.
cite
Cites. Points at a source rather than a note — the target is a bibliography-style reference, not another knowledge-base file.
quote
Quotes. Points at a specific excerpt anchored in a source, for a direct quotation rather than a general citation.

How a target resolves

Minerva tries a target against your notes in order and stops at the first match:

  1. Exact file path.
  2. Filename, case-sensitive.
  3. A note's aliases: frontmatter, case-insensitive.
  4. Filename, case-insensitive and slugified — punctuation and spacing don't have to match exactly.
  5. Full path, slugified.
  6. A unique tail of a nested path (so [[raft]] can resolve to journey/raft.md).

The same resolver drives graph indexing, click-to-navigate in preview, and the hover preview — a link goes to the same place everywhere it's shown.

Ambiguous targets

If more than one note could satisfy a given step above, Minerva takes the first one it finds and doesn't warn you. Keep filenames distinct, or lean on aliases: frontmatter to make the intended target unambiguous.

In the source editor, clicking a link navigates to it; ⌘-click (or Ctrl-click) places the cursor inside it to edit, the same convention as footnotes.

Backlinks

Every link is indexed into the graph as a triple from the source note to the resolved target, using a predicate specific to its type — an untyped link becomes a references triple, a [[supports::x]] link becomes a supports triple, and so on. The right sidebar's Backlinks panel queries the graph for every note that links to the one you're viewing, and shows each with its link type's label and color, so you can tell at a glance whether an incoming note supports, rebuts, or merely references the current one.

Gotchas

  • Links inside code don't count. A [[...]] written inside a fenced code block or inline `code` span is left as literal text — it's never indexed or rendered as a link.
  • No nested brackets. A link ends at the first ]] it finds, so a literal ] inside a target or display string will truncate the link early rather than being escaped.
  • Unresolved links don't stand out. A target that doesn't match any note still gets indexed — as a link to a not-yet-existing file — but it renders the same as a resolved one. Clicking it is a silent no-op: no note gets created and there's no error dialog, it just doesn't do anything. Check the Backlinks panel or graph query results if you suspect a link isn't landing where you expect. See Navigation → Wiki-links for the click and hover-preview behavior in more detail.
  • Frontmatter links are plainer. A wiki-link written as a frontmatter value (e.g. in a custom property) only supports [[target]] and [[target|display]] — no type prefix, no anchor. Frontmatter values are treated as bare references.
