Docs/Settings/Formatter

Formatter

The Formatter tab in Settings lists every deterministic markdown normalization Minerva knows how to apply — trailing-whitespace cleanup, frontmatter tidying, footnote conventions, and more — each as its own checkbox with a title and a plain-language description. Formatting itself runs on demand, from Refactor ▸ Format, not automatically on every save; this tab only controls which rules fire the next time you run it.

House style, and everything else opt-in

Rules aren't all-on or all-off together. Minerva ships a curated house style — a subset chosen because each rule is safe and uncontroversial: it tidies whitespace, list markers, frontmatter shape, or Minerva's own link hygiene without ever changing the meaning of your prose, your heading levels, or the words you wrote. House-style rules are on by default. Every other rule — anything opinionated enough that it could surprise a writer, like heading capitalization, smart-ellipsis substitution, or spelling autocorrect — is off by default and stays off until you check its box.

Toggling any rule, in either direction, writes an explicit override; a rule with no override falls back to whether it's in the house-style set. Overrides are stored per-project in .minerva/formatter.json, so they travel with the thoughtbase — open the project on another machine and you get the same formatting behavior, not a fresh set of per-machine defaults.

"Restore house style"

The button above the rule list clears every explicit enable/disable override in one step, so each rule falls back to the curated default — house-style rules on, everything else off. It's disabled when you're already at house style (no overrides to clear), and it doesn't ask for confirmation — there's nothing destructive about it, since your notes aren't touched until you next run Format. One thing it deliberately leaves alone: per-rule configuration. If you'd changed a rule's own setting — for instance, how many consecutive blank lines to allow — that value survives a restore. The button resets which rules run, not how the ones you've tuned are configured.

Rule categories

Rules are grouped into six categories, applied in this order — structural passes first, so later rules see an already-normalized document shape. A handful of real examples from each:

YAML frontmatter
Structural tidying of the YAML block — no value rewrites beyond de-duplication. Compact frontmatter (house style) strips leading and trailing blank lines inside the block. Dedupe YAML array values (house style) collapses tags: [a, a, b] to tags: [a, b], first occurrence wins. Sort frontmatter keys (opt-in) imposes a consistent key order.
Headings
Heading increment (opt-in) clamps an out-of-order jump — H1 straight to H3 — down to the previous level plus one; the document's first heading is always accepted as-is. Capitalize headings (opt-in) applies a chosen case style (title case, sentence case, or lowercase) with a configurable list of proper nouns to preserve verbatim.
Content
Proper ellipsis (opt-in) collapses three consecutive dots (...) into a single … character. Wrap bare URLs (opt-in) turns a bare https://… into an angle-bracket or link form. Auto-correct common misspellings (opt-in) runs a small, deliberately conservative starter dictionary — extendable via a per-rule config rather than expected to catch everything out of the box.
Footnotes
Footnote reference after punctuation (opt-in) moves a reference marker that lands before sentence-ending punctuation to after it: word[^1]. → word.[^1]. Move footnotes to the bottom (opt-in) collects every [^name]: … definition, continuation lines included, and re-emits them as a single block at the document's end, in document order.
Spacing
Trailing whitespace (house style) strips trailing spaces and tabs from every line, leaving code fences, frontmatter, and math untouched. Collapse consecutive blank lines (house style) caps runs of blank lines at a configurable maximum — default 1.
Minerva-specific
Canonical wiki-link extension (house style) enforces one style for wiki-link targets, always with .md or always without — typed links like [[cite::…]] are left alone since they target sources, not files. Unique heading slugs (house style) suffixes a duplicate heading anchor (Overview + Overview → Overview + Overview 2) and cascades the rename into any incoming [[note#old-slug]] links.

Gotchas

  • Formatting is on demand, not on save. There's no background pass that rewrites a note the moment you save it. Rules only run when you invoke Refactor ▸ Format — on the active note, or on every .md file under whatever you've selected in the left sidebar (multi-select with ⌘-click, ⇧-click, or ⌘A). Toggling a rule in Settings changes nothing about notes already on disk; it only changes what happens the next time you run Format.
  • Nothing is retroactive. Following on from the above: a note you formatted last week under an old rule set stays exactly as it was written. There's no "re-format everything" prompt triggered by a settings change — if you want the new rule set applied project-wide, select the whole tree in the sidebar and run Format yourself.
  • It's global, not per-note. There's no frontmatter flag or per-file switch to exempt a single note from formatting — the rule set in this tab applies uniformly to whatever you run Format over. If a note needs different handling, leave it out of your sidebar selection when you invoke the command.
  • Ignore the tab list's "On-save rules" subtitle. The Settings sidebar's own tab listing labels this section "On-save rules" — that's a holdover from an earlier design and doesn't match current behavior. Nothing runs on save; go by the on-demand behavior described above.
  • Restoring house style doesn't touch per-rule configuration. Clearing your on/off overrides is not the same as clearing everything — a tuned value like a custom blank-line maximum persists across a restore. Only the enabled/disabled state resets.
