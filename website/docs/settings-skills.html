Skills

The Skills tab in Settings is where a skill catalog gets managed — but enabling, disabling, reassigning between menus, and reordering are already covered in full at Thinking tools → Managing & authoring. This page covers the two things that live here and nowhere else: importing your own skill file into the catalog, and setting a per-skill model override.

Importing a skill

The Import skill… button at the top of the tab opens a native file picker that accepts either a single .md file or a folder containing a SKILL.md (the same two shapes described in Managing & authoring — a bare file or a Claude-style skill folder). Whatever you pick is validated and, if it passes, copied into ~/.minerva/skills/.

What gets checked
Before anything is copied, Minerva parses the file's YAML frontmatter and rejects it outright if required fields — name, description, a valid menu, a recognized outputMode — are missing or malformed. A folder without a SKILL.md inside it is rejected the same way. Nothing lands in your skills folder until the file is confirmed valid.
Colliding with a stock skill
User skills are additive only — they can never shadow a built-in one. If the id you're importing matches a stock skill's id, the import is rejected before the copy happens, and Settings shows the reason inline: a built-in skill already uses that id, and the fix is to disable the stock one and give yours a different id.
Colliding with another user skill
Same rejection, different message: you already have a skill using that id. Rename the id in the file's frontmatter and try again.
Canceling the picker
Dismissing the file picker without choosing anything is a silent no-op — no error, nothing imported, nothing to dismiss.
On success
The skill catalog reloads and the native menu rebuilds immediately — your import shows up in its declared menu (or wherever Managing & authoring's reassignment moves it) without restarting Minerva.

Two adjacent buttons round out the row: Reveal skills folder opens ~/.minerva/skills/ in your OS file manager (creating it first if it doesn't exist yet), and Reload re-scans that folder without going through the import dialog — useful after hand-editing or dropping a file in directly.

A rejected import still shows you why

Every rejection reason above — bad frontmatter, a missing SKILL.md, a stock or user id collision, a filename that already exists in the folder — surfaces as the exact underlying message in an inline message beneath the button row, not a generic "import failed." You never have to guess which of the several validation checks tripped.

Per-skill model override

Each skill row carries a model picker alongside its menu-reassignment dropdown. Left on its default option, the skill runs on whatever model it would have used anyway — its own model: frontmatter preference if it declares one, otherwise the AI tab's global default model. Picking a specific model here pins that one skill to it, regardless of what the AI tab's default is set to.

Default option label
The picker's empty option is never a bare "Default model" — it names whichever model would actually apply, e.g. "Default · Claude Sonnet 5", so you're not guessing what "default" resolves to for that particular skill.
Resolution order
A skill invocation resolves its model as: this override, if set → the skill's own model: preference, if it declares one → the AI tab's global default model. The override set here always wins over a skill's own stated preference.
Storage
Overrides are keyed by skill id in a single map alongside the API key, the global default model, and the effort setting — the same AI tab settings object, saved together when you close the Settings dialog. It's machine-global, like menu-config.json: the same overrides apply no matter which thoughtbase you have open, but they don't travel with a project to another computer.

Gotchas

  • Overrides don't survive a restart yet. The override map is written to disk correctly when you close Settings, but the setting isn't read back on the next load — so a per-skill model choice quietly reverts to "Default" the next time you reopen Minerva (or the Settings dialog after a reload). Re-set it if a skill seems to have forgotten its pinned model; nothing else in your settings is affected.
  • The override is per-skill, not per-menu or per-category. Two skills that share a menu can run on two different models; there's no bulk "set this menu to Haiku" control, only the per-row picker.
  • Importing doesn't create an override. A freshly imported skill has no entry in the override map — it runs on its own model: preference or the global default until you explicitly pick something for it.

For enabling, disabling, reassigning a skill to a different menu, or reordering it within one — the mechanics that make up the rest of this tab — see Thinking tools → Managing & authoring.
