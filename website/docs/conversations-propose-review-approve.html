Docs/Conversations/Propose, review, approve

The propose, review, approve loop

Minerva talks to a graph-backed knowledge base, and the one design decision that makes that safe is simple to state and easy to underestimate: the model never gets to write to it directly. Every AI-originated change to .minerva/graph.ttl — a new claim, a rewritten note, a proposed source summary — has to pass through a single choke point, the approval engine, before it becomes real.

The Trust Principle

The LLM proposes, the human confirms. Conversation output is evidence to be evaluated and filed, not an authoritative update to the graph. This is the most important design decision in Minerva — not a safety feature bolted on afterward, but the reason the approval engine (src/main/llm/approval.ts) exists at all.

Why proposals exist

An LLM is a source of claims about your notes, not an editor with commit rights. Treating its output as evidence means every graph mutation it wants to make is a suggestion until you look at it — so wrong claims, bad links, and hallucinated components stay quarantined as pending records instead of silently becoming part of what you know. The mechanism for that quarantine is a node type: thought:Proposal, with a thought:proposalStatus of thought:pending, thought:approved, thought:rejected, or thought:expired.

Internally, every LLM apply path funnels through one function, proposeWrite(), which takes an operationType (what kind of change this is) and a bundle of payloads (what it would actually write). What happens next depends entirely on that operation's approval tier.

The three approval tiers

Every OperationType the LLM can emit maps to exactly one tier in a policy table (DEFAULT_POLICY in approval.ts, lines 46–65). The tier decides whether proposeWrite() files a pending proposal, applies the write immediately and just logs it, or applies it with no record at all:

requires_approval
New claims (new_claim), evidence links (evidence_link), component creation (component_creation), note moves/renames (note_refactor), note deletes (note_delete), in-place note rewrites (note_rewrite), and proposed source properties (source_properties). proposeWrite() writes a thought:Proposal with status pending and stops there — nothing is applied until you act on it.
notify_only
Confidence updates (confidence_update) and status changes (status_change). The bundle is applied immediately via applyBundle(), but a thought:Proposal is still written — filed straight in as approved — so the change leaves an audit trail even though nobody reviewed it beforehand.
autonomous
Tag additions (tag_addition) and staleness flags (staleness_flag). Applied immediately with no proposal node written at all — proposeWrite() returns null. Low-stakes enough that even an audit-trail entry isn't worth it.

One override cuts across all three. Before dispatching on tier, proposeWrite() checks whether any node the bundle touches (affectsNodeUris) already carries thought:hasStatus thought:established — a SPARQL ASK-style lookup (anyNodeEstablished(), approval.ts lines 91–101). If so, the tier is forced up to requires_approval regardless of what the operation type's own policy says. A tag_addition against an ordinary note applies silently; the same tag_addition against a note you've marked established gets queued for your review instead. Once you've vetted something, the model can't quietly touch it again without asking.

The diff view

A pending proposal isn't a one-line description you have to trust — it's the literal payload bundle waiting to be applied, and reviewing it means reading that payload directly. Each payload in the bundle carries enough to reconstruct exactly what will land:

  • A note payload carries the full content of the file that would be created (plus the relativePath it would be filed at) — you read the whole note, not a summary of it.
  • A graph-triples payload carries the raw Turtle that would be merged into the store, along with the affectsNodeUris it introduces — the same triples the trust-integrity query later checks for approval provenance.
  • A note-rewrite payload carries the full replacement content for an existing note; approval captures the prior content as a pre-image first, so the operation is reversible even though what you're shown is the new version.
  • A note-delete or note-refactor payload names the path (or fromPath/toPath) being removed or moved.

A proposal can bundle more than one payload, and the bundle is atomic: approving applies every payload in order, rejecting discards all of them, never half. This is the same mechanism the Proposals panel renders as an expandable card per payload — that page documents the panel's UI in detail (the status tabs, the keyboard shortcuts, the project-wide scope); this page is about what makes the payload trustworthy to read in the first place: it's the actual write, not a paraphrase of it.

Approving and rejecting

Once you've read the payload, the decision is one keystroke: y to approve, n to reject, both handled by approveProposal() / rejectProposal() in approval.ts. Approving applies the bundle and flips status to approved; rejecting flips status to rejected and applies nothing, but the proposal node itself stays in the graph either way — reviewed history, not a queue you empty. See Proposals for the full keystroke reference, the status-tab filtering, and what the panel shows you while a card is collapsed.

Auto-expiry

Every proposal is stamped with an autoExpires timestamp at creation — seven days out by default (write.expiryDays ?? 7), configurable per write. There is a real function that enforces it, expireProposals(), which walks every still-pending proposal past its autoExpires date and flips it to expired.

What doesn't exist is anything that calls that function on a schedule. expireProposals() is wired to a single IPC channel, proposal:expire, exposed on window.api as api.proposals.expire() — but nothing in the renderer currently invokes it, and there's no timer in main running it in the background. In practice a proposal past its expiry window doesn't flip itself to expired; it just keeps showing as Pending until something calls that IPC method, which nothing currently does. Treat autoExpires as a recorded intent rather than a guarantee — Proposals covers this same finding from the panel's side, in its Gotchas section.

Gotchas

  • "Applied immediately" still isn't invisible. notify_only operations write to the graph before you ever see them, but they still leave an approved proposal behind — check the Approved tab in the Proposals panel if you want to know what an autonomous-feeling AI action actually did.
  • autonomous operations leave nothing to audit through proposals. Tag additions and staleness flags never create a thought:Proposal at all. If you want a record of every graph write regardless of tier, the Proposals panel won't show these — you'd need to look at the graph directly.
  • Escalation is per-write, not per-conversation. The established-node check runs against the specific affectsNodeUris a given bundle touches, computed fresh on every proposeWrite() call — there's no session-level flag that makes an entire conversation more cautious once it brushes an established node once.
  • Approving a bundle with zero payloads throws rather than silently succeeding. That's a deliberate refusal in approveProposal() — an empty bundle means something upstream filed the proposal incorrectly, and the engine surfaces that as a bug instead of a no-op approval.
