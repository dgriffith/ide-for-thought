Docs/Thinking tools/Running a skill

Running a skill

Pick a skill from the Learning, Research, or Analysis menu (or the editor's right-click menu) and Minerva gathers whatever context that skill declared it needs from the note you're in, then runs it. Almost every stock skill hands its result to you as a reviewable proposal — nothing lands in your notes or the graph without a keystroke from you.

From menu click to running

A skill is just a registered thinking tool, so invoking one from a menu, the editor's right-click, or the command palette all funnel through the same path: the click sends the tool's id over the tool:invoke IPC channel, the renderer gathers exactly the context fields that skill's context: frontmatter declared (the current note's full text, your current selection, a claim under the cursor, related or tagged notes, or — for Source-scoped skills — the active source's metadata and body), and then runs it.

1. Gather context
Only what the skill asked for is collected — a skill that lists fullNote gets the current note's text and path; one that lists selectedText gets your highlighted passage; one that lists claimUnderCursor resolves the thought:Claim at your cursor. Nothing is sent that the skill didn't declare it needs.
2. Ask for parameters (if any)
A skill can declare a small parameters form — a dropdown, a text field, or a note picker — that opens as a dialog before anything runs. Excavate's "Analysis depth" (Quick / Standard / Deep) is a stock example. Skills with no parameters skip straight to running.
3. Run
Most stock skills open a new conversation seeded with a system prompt and an auto-fired first message built from your context — you watch it think and respond like any other conversation. A handful of skills (marked for direct output) instead run in a compact bottom panel with a streaming "Thinking…" view and no chat back-and-forth.
4. Land as a proposal
When a skill's work involves writing to your notes or graph — filing a claim, proposing linked evidence, drafting a source summary, rewriting a note — it calls a tool like propose_claims or propose_source_properties, which files a thought:Proposal through the approval engine. Nothing is written until you approve it.
The trust principle still applies

A skill is a prompt template, not a shortcut around the approval engine. Whatever conversation a skill opens is bound by the same rule as a conversation you started yourself: the LLM proposes, the human confirms. See The propose, review, approve loop for how the approval tiers work and Proposals for how to review and act on what a skill files.

Where the result actually shows up

What you see after a skill runs depends on its outputMode, set by whoever authored it:

Open a conversation
The default for nearly every stock skill. The menu click opens a new conversation tab pinned to your current note, with the skill's system prompt and first message already in place. You read the model's reasoning as it comes in, same as any chat — and if the skill's job is to propose a graph change, that proposal appears the same way any conversation-filed proposal does: as a pending card, reviewable from the Proposals panel.
Direct output panel
A small number of skills (Excavate is a stock example) run in a bottom dock instead of opening a conversation: a streaming "Thinking…" view, then the finished text with Save as Note, Append to Current, and Copy buttons. This is a separate, older mechanism from the proposal system — choosing "Save as Note" writes the file immediately rather than filing a thought:Proposal. The explicit button click is still your confirmation step; it's just a different one than the diff-and-approve flow.

Gotchas

  • A skill can refuse to run before it ever reaches the model. If a skill declares requiresSelection and you haven't highlighted anything, the menu item fails fast with a message telling you to select text first — the right-click menu hides the entry entirely in that case. Other skills check their context at prompt-build time instead: a claim-scoped skill invoked with no thought:Claim under the cursor throws a specific, readable error ("right-click on a claim line first") rather than sending an empty prompt to the model.
  • Running a skill over a note with nothing relevant in it doesn't error — it just produces a thin result. A source-summarizing skill invoked with no extracted body text says so plainly in its first message rather than fabricating a summary; other skills without that guard will still run and the model will do its best with sparse input, which usually means a proposal not worth approving. Reviewing the diff before you approve is what catches this, not the tool refusing to run.
  • The skill only sees the context it declared, not everything about the note. A skill listing only selectedText never sees the rest of the note, even though you invoked it while that note was open — if a skill seems to be ignoring context you'd expect it to use, check what its context: list actually requests (see Managing & authoring).
  • Cancel stops the run, not the proposal. The direct-output panel has a Cancel button while it's streaming, which stops that call. A skill running as a conversation is cancelled the same way any conversation send is — but if the model already made its tool call before you cancelled, whatever it proposed is still sitting in the Proposals panel; cancelling doesn't retract a proposal already filed. Reject it there if you don't want it.
