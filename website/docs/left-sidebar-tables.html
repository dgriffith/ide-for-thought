Tables

The Tables panel lists every .csv file in your project as a queryable table. Each one is registered as a live DuckDB view the moment it appears on disk — the panel isn't a browser for markdown tables or their CSVW triples, it's a directory of your project's actual CSV data, ready to query with SQL.

Not the same "tables" as the Notes & Tables page

Tables & CSV covers markdown pipe tables written inside a note and how each one is extracted into .minerva/graph.ttl as CSVW triples on save. This panel is unrelated: it only ever lists standalone .csv files sitting in your project folder. A markdown table inside a note's prose never appears here, and a CSV file's rows never appear as a markdown table anywhere — the two pipelines don't intersect except that both eventually write shape information (columns, types) into the same graph.

How a CSV gets here

On project open, Minerva walks the project folder and registers every .csv file it finds as an in-memory DuckDB view — the view is lazy, so DuckDB re-reads the file from disk on every query rather than caching stale content. The file watcher keeps this live afterward: adding, editing, or deleting a .csv anywhere in the project registers, re-registers, or drops its view automatically, and the panel refreshes to match. There's no import step and no dialog — drop a CSV in the folder and it's queryable.

The SQL identifier for a table is derived from its path by default (slashes and punctuation become underscores — notes/data/2024-experiment.csv becomes notes_data_2024_experiment), but you can pin an explicit name. A companion markdown note in the same folder with a matching filename stem (experiment.csv ↔ experiment.md) can set table_name: in its frontmatter to override the derived name — useful for giving a table a shorter or more memorable identifier than its path would produce.

Two CSVs, one name

If two different CSVs would derive the same table name, the second one is skipped rather than silently replacing the first's view — you'll see a toast pointing at the conflict, and the fix is a table_name: override on one of the companion notes to disambiguate. The skipped file's data simply isn't queryable until you resolve the collision.

What each row shows

The panel is a flat, alphabetically-sorted list (by file path) with a filter field above it that matches against both the table name and the file's relative path as you type.

Table name
The SQL identifier — the derived or overridden name described above — shown in monospace as the row's primary label.
Row / column counts
A live count queried straight from DuckDB — 3 rows · 5 cols, for example — not a cached figure from when the file was first registered.
File path (on hover)
The CSV's project-relative path isn't printed in the row itself, but it's the row's tooltip — hover to confirm which file a given table name maps to.

Clicking a table

Clicking a row doesn't open the CSV file or jump anywhere in a note — it opens a new SQL query tab pre-filled with SELECT * FROM <table name> against that table, so you land straight on its data. From there it's an ordinary compute-cell-style query surface: edit the SQL, re-run it, and it executes against the same in-memory DuckDB instance the panel itself is backed by.

Right-clicking a row opens a context menu with four actions:

Query (SELECT *)
Same action as a left click — opens the query tab.
Copy Table Name
Copies the SQL identifier to the clipboard, for referencing the table in a query you're already writing elsewhere (a compute cell, for instance).
Open CSV
This is "opening the underlying CSV" — it opens the raw .csv file itself as a file tab, the same as selecting it in the notes tree. There's no separate export or view-as-table step; you're looking at the plain-text file on disk.
Reveal in Finder
Shows the CSV file in the OS file browser.

Gotchas

  • Empty project shows a hint, not a blank pane. With no CSVs registered, the panel reads "No tables yet. Drop a CSV into the thoughtbase." instead of an empty list.
  • A table with no header row is still queryable, just awkwardly. DuckDB's CSV auto-detection infers a header when it can; if a file genuinely has none, columns come back as generic auto-generated names rather than anything meaningful. There's no markdown-style caption concept here at all — a CSV file has no title beyond its filename and derived table name.
  • Reads are live, but registration needs the watcher (or a rebuild) to notice a brand-new file. Editing an already-registered CSV is reflected immediately — the DuckDB view re-reads on every query. Adding a new .csv or renaming one relies on the file watcher to register it, which is normally instant; if a table you expect doesn't show up, Query → Rebuild All Indexes forces a full re-scan of every CSV in the project.
  • This is a separate DuckDB instance from any per-note compute cells. The panel and its query tabs share one in-memory database per project — every registered CSV is queryable from any query you open, and none of it touches .minerva/graph.ttl directly (only column names and types are mirrored into the graph, not row data).
