Search

Press ⌘⇧F (or Ctrl⇧F) to open Find in Notes… — a project-wide search across every file's actual content, not just titles. Results update live as you type, grouped by file, and clicking any match opens the note with the cursor placed at that exact line and column.

Opening it

Search lives in FindInNotesDialog.svelte, a modal dialog with a segmented toggle between two modes: Find and Find and Replace. It's reachable three ways, all landing on the same dialog:

⌘⇧F
Opens in Find mode. Registered as a native Electron menu accelerator on Edit → Find in Notes…, not in the app's own keymap handler — it fires whether or not the editor has focus.
⌘⇧H
Opens the same dialog directly in Find and Replace mode, via Edit → Replace in Notes…. You can still switch modes with the segmented control once it's open.
Command palette
"Find in Notes…" is listed under the Edit category in the command palette (⌘K), for when your hands are already there.
Not the same as ⌘F

⌘F and ⌘H — without Shift — open CodeMirror's built-in search panel inside the current editor tab only. Search proper (⌘⇧F) is the project-wide version: same underlying idea, different scope. If you're only turning up matches in the file you already have open, you pressed the wrong one.

What gets searched

This is a literal, on-disk grep — not a graph query. It reads every indexable file fresh from the filesystem on each search and scans line by line for the pattern; it never touches .minerva/graph.ttl, so it doesn't know about tags, typed links, or frontmatter as structured facts. If a tag or a linked title is spelled out in a file's text, a text match will still find it — but there's no separate graph-aware match type, no "matched because it's tagged X."

File types
Every indexable file in the project: notes (.md), Turtle blocks and standalone RDF (.ttl), CSV data (.csv), and Python compute cells (.py). The same extension set the sidebar and file watcher treat as first-class notebase files — the same folders are excluded too (.git, node_modules, .minerva, .obsidian, dotfiles).
Body content
Yes — this is the primary thing being matched. Every line of every file is scanned against the pattern.
File and note names
No. Only file contents are matched against the pattern; a filename that happens to match your query but doesn't contain it in the body won't turn up. The file's relative path is shown as each result group's header, but it isn't itself searched — that's what Quick switch is for.
Graph facts (tags, typed links, frontmatter)
Not as structured data. Search bypasses the knowledge graph entirely — it's a text scan, so a tag like #draft or a wiki-link's raw [[target]] syntax matches only because the literal characters are present in the file, the same as any other text.
Case sensitivity
Case-insensitive by default. Toggle the Aa button next to the search field to match case exactly.
Regular expressions
Off by default — a plain query is treated as a literal substring (special regex characters are escaped automatically). Toggle the .* button to write a real pattern instead.

Results: grouping, ranking, and jumping in

Results are grouped by file and sorted alphabetically by relative path — not by relevance, match count, or recency. There's no scoring: a query either matches a line or it doesn't. Within a file, matches appear in document order, top to bottom. Each file group is an expand/collapse accordion, useful when one file has a long run of matches you want out of the way.

Click any match row to jump straight to it: the note opens in the editor and the cursor lands at the exact line and column of the match, scrolled to the vertical center of the view. This is a real cursor placement, not just "open the file" — you can start typing immediately.

Live search, not search-then-Enter

Typing into the pattern field re-runs the search automatically, debounced by 200ms — there's no Enter key to press, no separate "search" button. Toggling case-sensitivity or regex mode re-runs it the same way. A running match/file count sits in the dialog header once results come in.

Find and Replace

Switching to Replace mode adds a replacement field and a per-match checkbox next to every result (all checked by default), plus file-level checkboxes for bulk toggling. Replace Selected applies only the checked matches; Replace All applies every current match regardless of checkbox state. Each result row previews what the line will read after replacement. Replace re-reads every target file from disk at apply time — rather than trusting what was on screen at search time — so a file changed since your last search is replaced against its current content, not a stale snapshot.

Gotchas

  • Reads from disk, not from memory. Search has no dependency on the graph index — it's a fresh filesystem read on every keystroke. But that cuts both ways: if you have unsaved edits in an open editor tab, Search won't see them (or will still show old text) until the file is actually saved to disk.
  • No fuzzy matching here. Unlike Quick switch's multi-strategy fuzzy scoring, Search is a literal substring or regex match — nothing in between. A typo in your query simply won't match.
  • A literal ] or regex metacharacter needs the right mode. With the regex toggle off, everything you type — including characters like . or * — is escaped and matched literally. Turn on .* if you actually want regex semantics.

Search vs. Quick switch vs. the command palette

The three sit side by side in the left sidebar for a reason — each answers a different question:

Search — ⌘⇧F
Find a passage — a full-text scan of every file's actual content, across the whole project. Use it when you remember something you wrote but not which note it's in.
Quick switch — ⌘P
Jump to a thing — a note, source, or saved query — by fuzzy-matching its title or path. Never looks inside a file's content. See Quick switch.
Command palette — ⌘K
Run an action — a menu command, a skill, a setting — by name. See Command palette.

If you know a note's title, Quick switch gets you there fastest. If you're hunting for a specific line of text and don't know (or don't remember) which note it lives in, Search is the tool — it's the only one of the three that looks inside file content rather than titles or command names.
