Turtle / RDF

Most of the knowledge graph is built for you — titles, tags, links, frontmatter, and table data are all extracted automatically as you write. But sometimes you know the relationship you want to assert more precisely than any auto-extraction could infer it. A fenced turtle block lets you drop hand-authored triples straight into a note; Minerva parses them on save and merges them into .minerva/graph.ttl alongside everything it extracted on its own.

Syntax

Mark a block with the turtle language tag. Anything inside is parsed as Turtle, not rendered as a code sample:

```turtle
Opening fence. The language tag must be exactly turtle — lowercase, no aliases like ttl or rdf are recognized. A block with any other tag (or no tag) is left as an ordinary code block and never reaches the graph.
this:
Self-reference prefix. Stands for the current note's own IRI. Use it as the subject when the triple is about the note itself — the common case.
```
Closing fence. Same as any fenced code block. Everything between the fences is handed to the Turtle parser verbatim.

A short, realistic example — typing a note as a glossary term and linking it to a broader concept:

```turtle
this: a thought:Term ;
    thought:hasStatus thought:established ;
    minerva:relatesTo <https://minerva.dev/ontology#Provenance> .
```

On save, this block contributes three triples — all with this: resolved to the note's own IRI — into the note's slice of the graph, right next to the title, tags, and links Minerva extracted from the rest of the file.

Prefixes

You don't need to declare the standard prefixes yourself. Minerva prepends them to the block before parsing — the same fixed set used everywhere else in the graph: minerva, thought, dc, rdf, rdfs, xsd, csvw, owl, prov, bibo, and schema, plus this: for the note itself. Write thought:Term or dc:title directly, with no @prefix line of your own.

Redeclaring a prefix

If your block already declares a prefix Minerva would otherwise inject — your own @prefix dc: …, say, or a custom @prefix ex: <https://example.org/> . — yours wins. Minerva only fills in prefixes the block doesn't already define, so you're free to point a standard prefix somewhere else or add prefixes of your own for IRIs outside the standard set.

How it merges into the graph

Every note has its own named graph in the store, keyed by the note's IRI — this is what lets Minerva cleanly drop and rebuild a single note's triples on reindex without touching anyone else's. A turtle block doesn't get a graph of its own: its triples land in that same per-note named graph, mixed in with the title, tags, links, and frontmatter triples Minerva generated automatically. There's no separate namespace or provenance marker distinguishing a hand-authored triple from an extracted one — once it's in the graph, it's just a triple in this note's graph.

Re-editing the block and saving again re-parses and replaces it, same as any other change to the note: reindexing clears the note's entire named graph first, then rebuilds it from scratch.

Gotchas

  • The tag is exactly turtle. ```ttl and ```rdf are not recognized — the block just renders as a plain code sample and none of its content reaches the parser.
  • A malformed block doesn't break the note. If a block fails to parse — a stray bracket, a missing period, an undeclared prefix you didn't mean to leave off — Minerva logs the error and skips that block. Every other part of the note (and any other turtle blocks in the same file) still indexes normally.
  • A skipped block fails quietly in the UI. There's no inline squiggle or banner marking a block as broken — check the main process console if triples you expected aren't showing up in a query.
  • Blank nodes are fine. _:x-style blank nodes work as you'd expect for structure you don't need to address from outside the block.
