Chatting with the AI

The conversations panel is a two-pane, mail-style chat: a list of open conversation tabs on the left, the active transcript and composer on the right. The model doesn't get your whole thoughtbase stuffed into its context on every turn — it gets a small set of tools and decides for itself when to search your notes, query the graph, or look something up on the web.

Opening a conversation

The panel lives beneath the editor and stays hidden until you ask for it — it's not a permanent fixture of the workspace. Every path into it lands on the same two-pane view:

Toggle the panel
View → Toggle Conversations (⌘⇧K) shows or hides the panel without touching any open conversation. Hiding it doesn't archive anything — your tabs are still there when you bring it back.
New conversation
The + button in the conversation list, View → New Conversation, or the toolbar's New Conversation button above the editor. This starts a freeform conversation — no note attached, regardless of what's open in the editor.
Ask about this note
Right-click a tab in the editor's tab bar → Ask About This.... This opens a new conversation whose contextBundle.notePath is set to that note, shown as a "From:" origin chip in the conversation's context rail — the note-scoped counterpart to a blank New Conversation.
Close a tab
The × on a tab, with a confirm dialog — "Close this conversation? You won't be able to reopen it." — because closing archives the conversation rather than merely hiding the tab. There's no reopen UI for an archived conversation, which is why the confirm exists even under the "don't add warnings" house rule.
A conversation's note origin isn't a lock-in

The context rail shows two things side by side when they differ: From: the note the conversation was started against, and Active: the note currently open in the editor, if you've since switched files. Both are passed to the model on every turn as plain sentences in the system prompt — "the user started this conversation from…" / "the note currently open in the editor is…" — so it can resolve "this note" against whichever one you mean, without the conversation being pinned to a single file for its whole lifetime.

How the AI is scoped to your thoughtbase

There is no step where Minerva serializes your graph, or the active note's full text, into the prompt on every turn. Instead the assistant is handed a fixed set of tools and a system prompt that tells it when to reach for each one — the model decides what it actually needs, per turn:

search_notes
Full-text search across the thoughtbase. The model's first move for "what have I written about X."
read_note
Reads one specific note by its relative path — typically a path search_notes or a citation just surfaced.
query_graph
Runs a SPARQL query against .minerva/graph.ttl for structural questions — what links to what, which notes share a tag, which claims cite a source. Standard prefixes are auto-injected, same as a ```sparql cell in a note.
describe_graph_schema
Fetches the full ontology TTL so the model can check class/predicate names before guessing at a non-trivial query.
web_search / web_fetch
For facts, current events, or documentation outside the thoughtbase — web_fetch reads a specific URL in full, typically one web_search just turned up.

The only always-on context is a few lines of plain text folded into the system prompt on every turn (buildConversationSystemPrompt in src/main/ipc/register-conversation.ts): today's date, the conversation's origin note path if any, and the currently-open editor note path if it differs. None of that is note content — just enough for the model to know which path "this note" refers to before it decides whether to go read it.

The trust principle still governs what comes back

Reading your notes and graph is unrestricted — the read tools have no approval gate, because reading changes nothing. But the two write tools available in conversation, propose_notes and propose_sources, only ever produce inline draft cards with Approve/Discard. Nothing the model reads or reasons about turns into a graph write on its own say-so — see The propose → review → approve loop.

Sending a message

The composer is a plain textarea: ⏎ sends, ⇧⏎ inserts a newline. Typing a leading / opens a filtered menu of built-in commands (like /compact, which summarizes older turns once a thread gets long) and any skill that declared a slash command — picking one runs it exactly as if you'd chosen it from a menu. A mic button next to Send drives local, on-device dictation into the composer when voice input is enabled.

Your message is echoed into the transcript immediately, before the model has replied — the send call can take anywhere from a second to tens of seconds, and without that optimistic insert your own message would appear to vanish from the composer with nothing to show for it.

Streaming responses

Replies stream in token-by-token, not all at once. Each chunk arrives over the conversation:stream IPC channel and is appended to a running buffer as it comes in; a three-dot "thinking" indicator sits at the head of the reply and stays visible through any mid-turn pause — including the gap while the model is blocked on a tool call between chunks of text — so the panel never looks stalled. The partial buffer is rendered through the same markdown pipeline as a finished message, so formatting doesn't visibly "snap" into place once the turn completes.

While a reply is streaming, the composer disables and its Send button becomes Cancel, which aborts the in-flight turn.

Referenced notes and citations

A citation in a conversation is a web source, not a link back into your graph. When the model uses web_search, each result it draws on becomes a numbered footnote under that assistant message — title, host, and the exact passage cited — and clicking one opens the URL in your default browser. There's a "cite" action next to each one that ingests the source into your Sources library and weaves a citation marker into whichever note the conversation is anchored to (its origin note, or the active editor note if it's freeform), the same mechanism as citing from anywhere else in Minerva.

References to your own notes work differently: the model just writes the relative path in its prose ("see research/thesis.md") per the system prompt's instruction to cite what it reads, rendered as plain markdown text — there's no separate "sources used" sidebar for thoughtbase reads, because reading a note doesn't need an approval trail or a footnote the way an external claim does.

Gotchas

  • The model picker and effort picker are per-conversation, not per-message. Changing the model on an existing tab only affects turns from that point forward; if the conversation had a reasoning-effort override the new model doesn't support, it's silently clamped to the nearest level it does (or cleared, for a model with no effort levels at all) rather than erroring on the next send.
  • Closing a tab is one-way. There's a confirm dialog, but there is no "reopen last closed conversation" — once archived, a conversation only resurfaces as an entry in whatever surface lists archived conversations, not back in the tab strip.
  • A conversation's citations are exclusively from web_search. If the model never calls that tool during a turn, the message carries no citations at all, even if it extensively read and referenced your own notes via search_notes/read_note.
