Docs/Right sidebar/Tags

Tags

The right sidebar's Tags panel shows the tags that appear on the current note — nothing else in the project — arranged as a hierarchy so a tag like #project/minerva/docs renders as nested rows instead of one long string. It's a read view: this panel doesn't add or remove tags itself. To change what a note is tagged with, you edit the note.

Not the same panel as the left sidebar's Tags

Minerva has two panels that both say "Tags," and they do genuinely different jobs:

Left sidebar → Tags is flat and project-wide — every tag used anywhere in the thoughtbase, alphabetical, with a count. It's for browsing the whole project's vocabulary and jumping to any note carrying a given tag, regardless of what you currently have open.

This panel, in the right sidebar, is scoped to whatever note is open in the active tab. It only ever lists tags that are actually present in that note's content — no other tag in the project shows up here at all — and it renders them as a tree rather than a flat list (TagsPanel.svelte, right-sidebar variant). Switch tabs and the panel's contents change with it; it is not a filtered view of the left sidebar's list, it's a different query answering a different question ("what does this note carry?" vs. "what tags exist?").

Reading the tree

A tag with slashes in it — #area/health, #project/minerva/docs — is treated as a path, and the panel builds a tree out of every such path across the note's tags. Segments are synthesized as parent rows even if nothing in the project is tagged with that exact shorter form: a note tagged only #foo/bar/baz still shows foo and foo/bar as rows above it, because they're implied ancestors, not because anyone tagged a note with just #foo.

Expand / collapse
Click the chevron on any row with children to fold or unfold that branch. Expand state persists locally (per-machine, not per-project) so the tree looks the same the next time you open the panel.
Click a leaf tag
Shows every note and source tagged with that exact tag in a "TAGGED #…" section below the tree — not just the current note. This is how the panel doubles as a jumping-off point: the tag you see here is scoped to the current note, but clicking it surfaces every other note in the project that shares it.
Click a parent tag
Shows every note and source tagged at-or-under that prefix — "TAGGED UNDER #…" — a superset of clicking each child leaf individually. Useful for a broad sweep, e.g. every note under #area/health regardless of how deep the specific tag goes.
Accent marker
A row for a tag literally present on the current note is tinted with the accent color, distinguishing it from a synthesized ancestor row that exists only to hold the tree together.
Filter field
The ribbon's search box filters the tree by substring. A match keeps its ancestor chain visible even if a parent branch was previously collapsed, so you can see where in the hierarchy the hit lives.

Adding and removing a tag

There's no input field or delete control in this panel — it only reads. A tag is added to or removed from a note the same way any other content changes: by editing the note itself. Minerva recognizes tags written two ways, and this panel shows both together without distinguishing which form a given tag used:

Inline #hashtag
Type #tagname anywhere in the note's body. It's picked up as a tag the next time the note is saved and re-indexed — no special syntax beyond the leading # and a valid tag character to follow it.
Frontmatter tags: list
Add or remove an entry in the YAML tags: array at the top of the note. Many notes carry tags only this way, with nothing typed inline — the panel merges both sources so neither is treated as more authoritative.
Removing a tag
Delete the #hashtag text or the frontmatter list entry and save. There's no separate "untag" action — the panel simply stops showing a tag once the note no longer contains it in either form.

The panel re-reads the active note's content reactively, so a save that adds or removes a tag updates the tree immediately — no manual refresh. For the mechanics of how tags are extracted and indexed into the knowledge graph (the shared parsing that both this panel and the left sidebar's rely on), see Left sidebar → Tags.

How this feeds the rest of the app

Every tag on a note is indexed into .minerva/graph.ttl the moment the note is saved, the same as titles, wiki-links, and frontmatter metadata generally. That indexing is what makes both Tags panels, tag-based SPARQL queries, and the auto-tag skill's "don't repeat an existing tag" check all possible — this panel is simply the narrowest lens onto that same graph data, filtered down to one note.

Gotchas

  • No tags in the note, no tree. A note with no tags at all — inline or frontmatter — shows a plain "No tags in this note" message instead of an empty tree.
  • A code block's # doesn't count. Text inside fenced or inline code is stripped before the panel looks for #hashtag matches, so a shell comment or a Markdown heading marker inside a code span won't accidentally show up as a tag.
  • Ancestor rows aren't "real" tags. A synthesized parent segment (e.g. foo above a note tagged only foo/bar) exists to make the tree readable, not because the project has a tag called exactly that — don't expect it to appear in the left sidebar's project-wide list unless some note is tagged with that shorter form directly.
