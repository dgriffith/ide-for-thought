Frontmatter

Frontmatter is a block of YAML at the top of a note, fenced by --- lines, that carries structured metadata the prose itself doesn't. Minerva parses it three ways at once: a handful of keys drive the app directly (a note's title, its tags), everything else becomes a graph triple on the note, and the whole block renders as an editable property list in the right sidebar — so the YAML, the graph, and the panel are always three views of the same data.

The frontmatter block

A note's frontmatter must be the very first thing in the file: an opening --- on line one, a closing --- on its own line below, and valid YAML in between.

---
title: The Attention Schema
tags: [neuroscience, consciousness]
created: 2024-03-01
---

The body of the note starts here.
---
Opening fence. Must be the first line of the file — nothing, not even a blank line, can come before it. Minerva only recognizes frontmatter that starts at byte zero.
key: value
A property. Standard YAML mapping syntax. Order is preserved when Minerva rewrites the block, and comments in the YAML survive edits made from the source editor.
--- (closing)
Closing fence. A second line containing only ---. Everything between the fences is parsed as one YAML document; everything after the closing fence is the note body.

If the YAML between the fences doesn't parse — a bad indent, an unclosed quote — the Properties panel shows the parse error and disables structured editing until you fix it in the source editor. The rest of the app degrades gracefully: a note with unparseable frontmatter still opens, indexes its links and body tags, and falls back to its filename for a title.

Recognized keys

Minerva ships with a set of canonical keys it understands well enough to map onto a specific graph predicate or a specific piece of app behavior. A generous set of aliases map onto the same canonical keys — write author or authors and both land as the same predicate as creator. You are not limited to this list — see Custom keys below.

title
String. Becomes the note's title everywhere in the app — sidebar, tab, backlinks, graph queries — overriding the first-H1 fallback. Indexed as dc:title, not as a generic metadata triple.
tags
List of strings. Merged with any inline #tag tags found in the note body into one tag set. A tag that only exists in frontmatter is indexed exactly like a body tag.
aliases (alias: alias)
List of strings (a single string also works). Alternate names this note resolves under for [[wiki-links]] — see Links → How a target resolves. Aliases containing [, ], |, #, or a newline are silently dropped, since they couldn't be written as a working [[alias]] anyway.
creator (aliases: author, authors)
String. Dublin Core author/creator.
description, abstract
String. Dublin Core description fields — a summary distinct from the note body.
publisher, subject
String. Dublin Core publisher and subject.
language (alias: lang)
String. Dublin Core language.
about
String (typically a [[wiki-link]]). Declares which source or note this note is about — maps onto the same predicate as subject, so the two are interchangeable.
created, modified
Date (YYYY-MM-DD) or datetime. Dublin Core timestamps. Note modified here is distinct from the file's actual on-disk mtime, which the graph indexer tracks separately regardless of frontmatter.
issued (aliases: date, year)
Date, datetime, or number. Publication date of the underlying source.
doi, isbn
String. Bibliographic identifiers (BIBO).
uri (alias: url)
String. Bibliographic URI/URL of the source.
pages (alias: pageRange), volume, issue, numPages
String or number. Bibliographic locators.
inContainer
String (typically a [[wiki-link]]). schema.org container reference — the journal, book, or site a source appears in.
accessedAt, archivedAt
Date or datetime. When a web source was accessed or archived — used by the source-tracking Research tools.
supports, rebuts
String (a [[wiki-link]] to a claim). Argumentation edges — materializes a thought:supports or thought:rebuts triple from this note to the target claim, same relationship a typed [[supports::…]] link expresses inline.
claim-kind (alias: claimKind), source-text (alias: sourceText)
String. Claim-mining metadata written by the Decompose-into-Claims tool.
extracted-by (alias: extractedBy), extracted-from (alias: extractedFrom)
String. Provenance for LLM-extracted claims — which tool or model produced this note, and what note or excerpt it was extracted from.
decomposes
String (a [[wiki-link]]). Points a decomposition note back at the source note it breaks down.
confidence (alias: confidenceValue)
Number, 0.0–1.0. Per-claim confidence score.
term, disambiguation
String. Glossary-note metadata: the term itself and a disambiguating note for when a term name collides.
seeAlso (alias: see-also)
List of [[wiki-links]]. Related glossary terms.
derived_from
String (a [[wiki-link]]). PROV-O provenance for a note derived from another — maps to prov:wasDerivedFrom.
derived_at, derived_from_cell
Datetime / string. Companion provenance fields written alongside derived_from for compute-cell-derived notes.
Aliases get rewritten, not preserved

Aliases exist so you aren't penalized for a natural spelling (author instead of creator), not as a second permanent form. Minerva's formatter canonicalizes frontmatter keys when it formats a note — an alias you typed gets rewritten to its canonical form on save. Write whichever one you want in the moment; don't expect the alias spelling to stick around.

Custom keys

Any key outside the canonical list is not rejected or dropped — it's indexed as-is. Minerva turns it into a graph triple using a generated predicate of the form minerva:meta-<key>, so a project-specific field like status: draft becomes a real, queryable edge even though Minerva has no built-in opinion about what status means. The Properties panel shows custom keys the same way it shows canonical ones — full editing, just without the accent-colored key and without appearing in the canonical-key quick-add suggestions.

One key is the exception: a publish: block (used by the static-site publishing feature) is deliberately excluded from graph indexing — it's a nested object of publication directives, not metadata about the note itself.

Value shapes

The Properties panel infers a type-specific editor from each value's YAML shape — a checkbox for booleans, a chip list for string arrays, a date picker for anything matching YYYY-MM-DD, a clickable chip for a single [[wiki-link]] value, and a raw YAML view (read-only in the panel, editable in source) for anything shaped like a nested object or a mixed-type list.

Gotchas

  • The opening fence must be line one. A blank line, a comment, or any character before the first --- means Minerva doesn't treat the block as frontmatter at all — it's read as ordinary note text instead.
  • Indentation is significant. Frontmatter is YAML, so it inherits YAML's indentation rules. A misaligned nested value is a parse error, not a best-effort guess — and a parse error disables the structured Properties editor until it's fixed in source.
  • Unquoted values can silently change type. date: 2024-03-01 parses as a date, not a string; version: 1.0 parses as a number; enabled: yes parses as a boolean, not the string "yes". If you want a literal string that happens to look like something else, quote it: version: "1.0".
  • A bracketed wiki-link in a list-like key gets eaten by YAML. Writing about: [[sources/foo]] looks like a wiki-link, but bare […] is YAML's array syntax — the outer brackets start a list and the inner brackets start a nested list, so YAML parses it as a one-element array containing a one-element array containing the string sources/foo. Minerva specifically detects this exact shape and recovers the intended [[sources/foo]] wiki-link, but any messier variant (a real multi-item list, extra text around the brackets) is left as whatever YAML actually parsed. When a value is meant to be a wiki-link, it's safest to quote it — about: "[[sources/foo]]" — so YAML never sees it as array syntax in the first place.
  • Nested objects don't reach the graph. A frontmatter value that's a mapping (not a scalar or a flat list) has no obvious predicate to materialize, so the indexer drops it rather than guess. The Properties panel still shows it — as read-only YAML — so it isn't invisible, just not queryable.
  • modified: in frontmatter isn't the file's real mtime. The graph's dc:modified triple is sourced from the file's actual on-disk modification time, independent of anything you write under a modified: key. Use the canonical key if you want to record something else — a "content last reviewed" date, for instance — without it conflicting with the real timestamp.
